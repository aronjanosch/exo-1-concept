# Learnings

Loose list of what we learned while working, for humans and agents. Source material for future skills. One entry per point: what, why, how to apply. Newest at the bottom of each section.

## Working with the initiator

- **The initiator decides game design.** Record only what they explicitly decided, in their words. Brainstorming, my own conclusions and technical findings are not decisions. Why: AI choices rest on assumptions, not on play experience. How: before writing to DECISIONS/CORE-LOOP/VISION, quote the exact decision back.
- **AI guesses turn into "decisions" by copying.** Example: "start radius 3 km" came from an AI research draft, moved into DECISIONS as "decided", then into the spike brief; nobody had chosen it. How: tag every number with its origin (decided, assumption, measured) and keep the tag when copying.
- **Design-relevant defaults in prototypes are assumptions.** Speeds, gravity, flight assists, look: label them as such in the spike README, don't present them as settled.
- **Everything is early and experimental.** A change the initiator tries is an experiment, not a rule. Do not write it into DECISIONS or other docs as settled; at most note it as an idea or direction to try.
- **Be brief.** Say a fact once, no repeated lists, no long recaps.
- **Spikes: progress over premature optimisation.** If it runs well on the initiator's machine, move on; optimise later.

## Local environment and tests

- **Never steal focus.** Check `WORKSPACE.md` in the code repo before running Godot. Prefer `--headless` for checks; for windowed runs use the contributor's wrapper (here `GODOT_AGENT_WORKSPACE=7 godot-agent`).
- **A window on a hidden workspace is throttled** (about 8 FPS). Frame times from such runs are worthless.
- **Godot releases all pressed keys when its window loses focus.** Scripted input via `Input.parse_input_event` then stops silently. Tests hold keys through their own input layer (`SpikeInput`), which is also closer to the proposed AgentBridge.
- **Screenshot readback plus PNG save costs 50-140 ms.** Exclude those frames from frame-time stats.
- **Bots must fly like players.** A blind bot at boost speed crashed into a hill and broke the run; give test bots simple controllers (altitude hold).
- **Scripted runs must not capture the mouse.** `Input.mouse_mode = CAPTURED` pulls pointer and focus to the game window even when the wrapper starts it unfocused on another workspace. Spike 5: no capture with `--auto-test`/`--auto-shot`.
- **Two agent sessions in one checkout collide.** A parallel session switched the shared working tree to its branch mid-edit. How: each session works in its own `git worktree`. Projects with the same name also share `user://`, so give result files and screenshots their own names.
- **Check the branch before every commit.** A worktree can be switched by another session without notice: `exo-1-origin-shift` moved from `spike/combined` to `spike/assisted-flight`, and a commit meant for one landed on the other. How: run `git branch --show-current` and `git worktree list` right before committing, and say which branch the commit went to.
- **Gitignored local files are missing in a new worktree.** `WORKSPACE.md` and `.godot/` (import cache, first start re-imports) do not come along. How: symlink `WORKSPACE.md` into the new worktree; it stays ignored. Delete the original and the link breaks.
- **Mouse capture can go stale on Wayland (Hyprland), assumed.** `_ready` sets `CAPTURED` before the window has focus, so Godot believes the mouse is grabbed while the compositor never locked it. A click handler that only acts on `mouse_mode != CAPTURED` then does nothing. Fix in the spikes: a click always sets `CAPTURED`, `NOTIFICATION_APPLICATION_FOCUS_IN` re-grabs unless Escape released it, scripted runs never grab. The initiator's manual test worked afterwards; the exact cause was not isolated (display driver x11 vs wayland not compared).
- **`godot --headless --path . --quit-after 5` without user args core-dumps** (exit 134, also on the unchanged spike commit; cause not investigated). For a syntax check of one script use `godot --headless --path . --check-only --script res://<file>.gd`.

## Git and spike states

- **Frozen spike states get annotated tags `spike/<n>-<name>`** (e.g. `spike/1-planet`), releases will use `v*`, so the two never mix. Why: old states must stay checkable for videos after branches are deleted; a tag also survives squash and rebase. Tag names differ from branch names (`spike/1-planet` vs `spike/planet`) because equal names make `git checkout` ambiguous.
- **Merge spikes normally, never squash,** or the single commits are gone. Spike code stays off `main` (throwaway, no approved proposal); an archive branch plus tags keep it reachable. Only findings go to the docs.
- **A branch that exists only locally is not safe.** `spike/combined` with all video commits was local only until pushed. Tags protect against deleting a branch, not against losing the disk.

## Godot and planet tech (spike 1)

- **Current renderer choice (initiator, 2026-10-04): Forward+ with Vulkan.** Revisit based on measured performance and visual correctness. Distant-surface depth precision is tested; a performance win over other renderers is not yet established.

- Derivative flat normals (`cross(dFdx, dFdy)`) are zero on sub-pixel triangles; `normalize()` gives NaN and it survives `mix(..., 0)`. Guard the length.
- Skirts must use the smooth normal, or they show as dark lines.
- Per-chunk origins cause hairline cracks between chunks; skirts fill them.
- Jolt `HeightMapShape3D`: square maps (at least 4 samples per side) use the native height field; non-square ones fall back to a mesh (4.7.2 source).
- Tangent-frame collision patches with curvature baked into the heights avoid the flat-plane error; let them overlap.
- Distance tests for the collision ring must ignore terrain amplitude (compare on the base sphere), or the ring grows about 5x.
- Depth: Forward+ uses reverse-Z with a float buffer (no z-fighting to 40 km); Compatibility behaves like a classic 24-bit buffer (z-fighting from about 500 m at cm gaps).
- Precision: no physics jitter standing still up to 16 km from the origin; walking breaks at 16 km (likely patch offsets), fine at 8 km.
- On a small planet "straight" flight leaves the planet in seconds. Horizon follow: add angular rate `up x v / r`. A levelling force fights intended climbs.
- Ring/LOD bursts on teleport cause 60-140 ms frames; continuous movement does not.

## Ships and walking inside (spike 3)

- Walker as a child of the ship, velocity relative to the ship, ship ignoring the walker's layer: holds up to about 400 m/s with roll (mm drift).
- Do not reparent bodies from `Area3D` signal handlers: reparenting re-fires the signals and a deferred call from there crashed Godot 4.7.2. Use a box test instead.
- Thin slabs (ramps) over uneven terrain let a capsule slip underneath; boarding on slopes needs its own design and test session.
- Stay on the essentials of a spike; when one detail (here the ramp) eats time, note it as open and move on.

## Float precision and origin shift (spike 5)

- **Check the obvious collider before blaming precision.** The 16 km "precision wall" from spike 1 was the parked ship standing in the walk path. How: log slide collisions (collider, normal, contact height) before drawing conclusions.
- **A safety net can hide the test.** The CPU height fallback kept the walker on the ground while the collision ring had silently built no patches. How: count frames where the net is the only thing holding the body.
- **Quadtree bounds on a cube-sphere: use the farthest corner.** `0.75 x edge` is too small for large cells on the curved face and pruned whole quadrants.
- **Godot sends moved bodies to physics only at a transform flush.** There is no flush between two `_physics_process` calls of the same tick. An origin shift in `_physics_process` let `move_and_slide` run against stale collision (falls through the floor). How: shift in `_process`.
- **Origin shift breaks silently wherever world and planet coordinates mix.** Example: `density_at` got a planet position and subtracted the centre again; the sky turned black only once the planet left the origin. How: one conversion function, type or name every position as world or planet-relative, and test with the planet away from the origin.
- **Physics survives far from the origin, the picture does not.** Jolt walking and landing worked up to 197 km from the origin; the error is in the float32 `view * model` on the GPU (about 2.5 px at 100 km for something 2 m from the camera). Measure in pixels, not only in physics.
- **Shift by whole metres and track the total in GDScript floats (64 bit).** Subtracting whole metres is exact here (0 mm jump in all runs), and the double total keeps the true position.
- **`AnimatableBody3D` with `sync_to_physics` (default on) does not follow a moving parent.** A ramp built as a child of the ship stayed at the ship's spawn point, so boarding over it failed. How: `sync_to_physics = false` for bodies that ride on a moving parent.
- **A difference of two far positions has the float resolution of the far distance.** Measuring steps relative to a planet 100 km away showed fake 7.8 mm stairs. How: measure in the frame where the body lives (world coordinates near the body), or in doubles.
- **Merging spikes: git conflicts are the small part.** Spike 3 + 5 had 2 text conflicts but 4 real interactions (double shift of a reparented child, origin assumptions, a hidden ramp bug, a changed default). How: rerun every test of both spikes on the merge and look for assumptions the other spike broke.
- **Movie maker needs a visible workspace.** On a hidden workspace (9) it wrote about 1 frame per second; on workspace 7 about 25-40. How: film on the visible agent workspace, and keep clips short with test options that skip to the scene (`--start-at=climb`).
- **To reproduce a bug on film, search headless with the same `--fixed-fps` first.** The test bot reacts per frame, so the frame rate changes what happens: the ship tumble ended in space at 60 fps (3 of 3) but landed at 30 fps.

## Flight feel research (2026-10-04, not playtested)

- **Flight assistance and throttle retention are separate choices.** Supplied video summaries describe both release-to-brake and sticky speed goals under assisted flight. Continuing to move can mean commanded cruise or inertial drift. Ask which release behavior the contributor wants before implementing; this remains open for the spike.
- **Keep transcript numbers as research notes.** The supplied summaries warn of ASR errors and omit original video links/dates. They support exploring control principles, not adopting exact speeds, acceleration ratios or keybindings as verified values.

## Assisted-flight spike (2026-10-04)

- **Curvature needs a force budget, not just a turning nose.** During acceleration, a large target-velocity error consumed all thrust and the ship climbed about 120 m in a nominally level high-speed run. Reserve curvature/drag support first, then spend the remaining vector budget on velocity correction. At 350 m/s, the fixture's 25 s run stayed within 2 m of its initial 2000 m clearance. These are measured fixture results, not full terrain guarantees.
- **Use terrain clearance for the local speed envelope.** A ship 600 m above the reference sphere but only 30 m above a mountain remained near 25 m/s in the fixture. Preview terrain over braking time and reduce clearance by descent stopping distance; sparse samples still cannot guarantee obstacle avoidance.
- **New speed targets change existing bot timeouts.** The 15 m/s vertical target needs about 133.5 s to reach 2000 m; the old 40 s phase silently tested a supposed vacuum glide inside atmosphere. Extend phase budgets and check attained altitude in the report. Full terrain/boarding/cabin regression had zero rescues and no passenger ejections across eight origin shifts.
- **Scope the physics question before blaming a language.** Godot exposes force/torque and custom integration while its solver runs natively. A few ships with aerodynamic surfaces are a different workload from fluid simulation. Sophisticated aerodynamics and native-code alternatives were discussed, not benchmarked or implemented. Sources: Godot stable RigidBody3D and CPU optimization documentation.

## Assisted-flight playtest follow-up (2026-10-04)

- **Passing motion checks does not establish flight feel.** The initiator reports abrupt ground starts/stops and heavy high-speed steering. Keeping 40 m/s² braking while increasing cruise from 25 to 350 m/s changes ideal stopping time from 0.625 to 8.75 s; curvature/drag support further reduces correction authority. New response-time targets are design candidates, not accepted tuning.
- **Nose, aim and trajectory are distinct feedback.** The current mouse-delta rotation has no persistent aim target; roll has no aerodynamic turning advantage. The supplied full transcript supports attitude, speed-limit and velocity HUD feedback but does not specify the exact mouse controller. Research references and pending options are in `exo-1-origin-shift/proposals/flight-feel-v2/`; no second controller is implemented yet.

## Flight translation tuning and worker cleanup (2026-10-04)

- **Separate the first comparison.** The initiator delegated with "your call"; translation tuning and a minimal piloting HUD were selected first. Ground cruise is 45 m/s, velocity response 0.35 s and thrust smoothing 0.15 s. Cruise-scaled authority stopped the real rigid-body fixture from 350 m/s in 2.75 s / 474.5 m and caught a small heading change within 2.5 s. Twenty-two controller checks passed; human feel judgment is still outstanding. Mouse aim and atmospheric banking remain later experiments.
- **Completed worker tasks still need to be reaped at scene exit.** Two full headless runs finished all gameplay phases then aborted. Symbolized core traced Main::cleanup through WorkerThreadPool::finish and bound Job destruction into an invalid GDScript mutex. Terrain/ring had no exit waits for pending task IDs. Adding `_exit_tree` waits and clearing pending jobs made the full run exit zero. A targeted removal test released 24 terrain and 60 collision jobs (weak references checked). Follow Godot's documented requirement to wait for every task; a completed task retains bound objects until reaped.
- **Rendered and fixture verification answer different questions.** Forward+/Vulkan cruise/landing exited zero with readable HUD and zero rescues. Full headless terrain/boarding/cabin regression after cleanup had zero rescues and seven clean origin shifts. Fixed-FPS statistics are not frame-time benchmarks. Review/results: `exo-1-origin-shift/proposals/flight-feel-v2/REVIEW.md`.
- **Responsive steering and quick release stops are different preferences.** Follow-up feedback: "far better", but both low/high release stops still feel too short. A possible next experiment is gentler neutral slowing plus explicit braking, keeping steering authority; not implemented yet. Requested reference altitude was added to the HUD alongside terrain clearance and visually verified in Forward+/Vulkan.
- **Gentle release and explicit brake tested separately.** Initiator accepted with "alright". Neutral piloted input uses 14 m/s² minimum or cruise/actual speed / 6 s; X overrides translation and uses the existing firm budget. Turning and unpiloted hover retain prior authority. Fixture: 45 m/s release reaches below 0.5 m/s in 3.57 s, 350 m/s release in 7.15 s versus X in 2.75 s (settled at 4 s). All 32 checks passed, including assist-off brake/manual resumption. Full and rendered terrain/cabin runs exited zero with no rescues; feel still needs a human playtest.
- **Planet follow preserves pitch, not altitude.** Initiator reports apparent automatic climbing. Code inspection: assisted gravity is fully cancelled; planet follow transports the frame and supplies curvature acceleration but does not remove an existing upward nose angle. Chase camera looks 10 degrees below the nose, so camera-level is not ship-level. This is a candidate explanation, not a reproduced diagnosis. Also distinguish ALTITUDE from GROUND over changing terrain. Next candidate check: log reference altitude, radial speed and nose pitch during level versus camera-level flight; no behavior change authorized or implemented in this discussion.
- **Small-planet orbit speeds collide with ordinary cruise values.** With the current 5000 m radius and 9.81 m/s² surface gravity, ideal vacuum circular speed is about 221 m/s and escape about 313 m/s at the reference surface. Being above circular speed can produce a bound ellipse, not necessarily escape. Ship mass does not change gravitational fall acceleration; usable thruster authority versus gravity determines hover capability. These are model calculations, not a decision to simulate orbital flight.
- **Measure ship attitude separately from camera attitude.** Initiator accepted the diagnostic with "okay gut dann weiter". NOSE/VIEW now display elevation above local horizontal; the distant visible horizon dips below it. At 2000 m reference altitude with scripted W and 60 Hz physics, level nose plus assist/follow lost 12.91 m in 60 s; initially level camera view (nose +10 degrees) gained 1700.33 m in 30 s; initially level nose with follow off gained 5071.91 m in 30 s. This supports the camera offset as a possible explanation for perceived climbing, not proof of the user's specific cause. Follow preserves pitch, with small measurable sinking rather than exact altitude lock. Physics/camera settings unchanged; 36 fixture checks and rendered Vulkan cruise/landing passed with zero rescues. NOSE/VIEW visually verified.
- **Finite gravity needs finite planet follow too.** Initiator wants full gravity inside atmosphere, softly gone by 6 km altitude; recommendation kept 6 km instead of 7. Model now uses 9.81 m/s² through 1200 m, smoothstep to zero by 6000 m; same envelope scales follow force, angular transport and preview. At 7000 m, unassisted rest did not fall over 5 s; assisted W with L enabled remained straight over 20 s. H still slows neutral input; disabling H enables coasting. Partial follow must integrate a turning velocity in the terrain preview: rotating planet-relative position alone underestimates travel distance by the influence fraction. Full-follow comparisons now use 1200 m rather than 2000 m, which is intentionally in the fade region. Small sinking remains (15.88 m in 60 s at 350 m/s); it is not an exact altitude lock. All 51 checks passed; full/rendered terrain/cabin regressions exited zero with zero rescues and no passenger ejections. HUD shows effective follow percent. These are behavioral checks, not performance benchmarks.


## Client-authority network spike (spike 4, 2026-10-04)

- **Shared snapshots must outlive local origin shifts.** Keep planet id plus planet-relative pose in the buffer; convert to the receiver's world only when displaying. Scalar-double centres/origins must be subtracted before creating a float32 Vector3. The spike's two live clients 200 km apart survived independent 10 km shifts. Float64 encoding preserves the source precision; it does not recover float32 precision already lost in a planet-relative Vector3.
- **A visual rigid-body transform can lag the solver by one step.** In the spike-4 fixture, `_process` read a ship transform one tick behind `PhysicsServer3D.BODY_STATE_TRANSFORM`. Shifting the visible pose rewound a 31 m/s ship by about 0.52 m each time. Using the current physics-server pose for dynamic-body shifts removed the repeated-position steps; measure the jump against that authoritative pre-shift pose. Shifts still run between physics ticks. Other spike worktrees were not changed or retested here.
- **Separate injected loss from ENet's native throttle.** Eight localhost physics processes caused adaptive unreliable throttling and additional unconfigured drops. The LAN fixture disables throttle deceleration (`throttle_configure(1000, 32, 0)`) and reports ENet bytes separately from snapshot payload. This isolates the experiment, not a WAN congestion-control recommendation. Disable default SceneMultiplayer peer relay when already relaying explicitly; this also removed errors on simultaneous client departures in the fixture.
- **Headless display rate is independent of snapshot rate.** An uncapped headless viewer sampled all seven remote histories about 1000 times/s. Cap the fixture's display at 60 Hz and avoid drawing HUD text headless; still send snapshots at 20/30 Hz. Final live eight-client interpolation/process means were 0.45–0.51 ms per display frame on this machine, not a universal frame budget.
- **Buffer latency must be labelled as total or extra.** Spike 4's 100/150 ms buffer is extra to simulated one-way delay. At 150 ms delay and 150 ms buffer, peers show roughly 300 ms-old states. At 30 Hz/150 ms extra buffer all fixed-seed replay cases through 10% loss had no holds and worst p95 delayed-path error 4.414 mm; actual eight-process traffic had a few brief holds. The local controller responded in one physics tick; the unpredicted host reference echoed inputs after about 467 ms with 150 ms input delay plus 150 ms snapshot delay plus the buffer.
- **Client authority does not assign contact authority.** Two independent Jolt spaces with delayed kinematic peer copies hit 13 physics ticks apart and disagreed by up to 3 m. A passenger can follow a remote ship using its id and local pose, but mutual ship impulses/docking still need a human ownership decision. No final contact rule was invented.
- **A rejoining owner restarts its snapshot sequence.** A newer shared timestamp plus a lower sequence must reset its display history and reject queued packets from the old lifetime. Otherwise the old history can reject the new packets as duplicates or interpolate a teleport. The live same-slot reconnect before the two-second expiry is tested.
- **Tester binaries come from the portable source package, not the worktree.** `build_binaries.py` unpacks `dist/exo-spike4-source.zip`, writes `export_presets.cfg` there and exports headless, so the root `project.godot` and the gitignore stay untouched. Needs the official 4.7.2 templates (1.2 GB tpz, folder `4.7.2.stable`, Arch's Godot accepts them). Presets without `include_filter`/`exclude_filter` print errors but still export; universal macOS refuses to export unless `textures/vram_compression/import_etc2_astc=true`; the macOS zip names the `.app` after `config/name`, not the export path. Keep `build_source.py`'s copy list in sync with `preload`s in `spikes/planet` (the newer flight code added `flight_hud.gd` and the stale package failed to compile `ship.gd`).
- **An agent session may run outside the Hyprland environment.** Without `HYPRLAND_INSTANCE_SIGNATURE` the wrapper falls back to plain `godot`, which fails with "Can't create the Wayland display server". Export `HYPRLAND_INSTANCE_SIGNATURE=$(ls -t /run/user/1000/hypr | head -1)` and `WAYLAND_DISPLAY=wayland-1` before `godot-agent`. To run an exported binary through the wrapper, put a `godot` symlink to it first in PATH; never write through such a symlink (one `cat > shim` overwrote the binary with a self-calling script).
- **Name spike branches without the number so the freeze tag can carry it.** Branch `spike/4-network` blocked the usual tag name `spike/4-network`; the freeze became `spike/4-client-authority`. Follow spike 1's pattern: branch `spike/<name>`, tag `spike/<n>-<name>`.

## Generator benchmark, GDScript versus Rust (spike 6, 2026-10-06)

- **Measure the demand before choosing the language.** Test workload (7 noise calls per vertex, scatter, 35x35 grid): A2 (optimised GDScript) 3.3 ms per chunk, Rust 0.65 ms, but the LOD asked for at most 114 chunks/s (350 m/s, depth 7) while 4 GDScript threads give about 1000/s. A 5-7x language gap did not matter at 9x headroom. Numbers and caveats: `SPIKE-6-REPORT.md`.
- **Godot's `FastNoiseLite` and the Rust crate `fastnoise-lite` 1.1.1 are bit-identical** (1000 points, all configs, ridged and OpenSimplex2S included). Rust variants can therefore be checked by checksum. The packaged crate has no licence file; upstream Auburn/FastNoiseLite is MIT.
- **GDScript worker threads stop scaling at about 8.** The same chunk job gave 1750/s at 8 threads and 370/s at 16 (cause not investigated). Rust kept scaling to 16. Cap GDScript generation at about 8 threads.
- **Most of an optimised GDScript chunk is interpreter overhead, not noise.** The noise calls are about 0.9 ms of 3.3 ms. Scalar maths, per-thread noise objects and inlining gained 24 percent; `Vector3` ops are not slower than scalar ones in the interpreter.
- **Terrain upload, not generation, was the first limit.** At depth 8 and 350 m/s the 4-uploads-per-frame cap (240/s) saturated before any worker did.
- **godot-rust costs 34 s per rebuild** with LTO and one codegen unit (3.7 s for the plain Rust binary). Parallel calls from worker tasks need the `experimental-threads` feature.
- **Parallel agents spoil timings.** Benchmarks run while two subagents compiled and ran Godot gave noisy numbers; rerun when the machine is quiet.
- **`godot --headless --import` writes `.import` files** for tracked images into the spike tree (untracked, not part of the spike).

## Rust extension builds (spike 7, 2026-10-07)

- **Cross-build Windows from Linux with llvm-mingw.** Target `x86_64-pc-windows-gnullvm`, linker `x86_64-w64-mingw32-clang` from `mise install github:mstorsjo/llvm-mingw`; no root, no Microsoft SDK licence. The DLL needs `libunwind.dll`: list it under `[dependencies]` in the `.gdextension` and the export copies it.
- **A fresh project's first headless import can abort on exit** (SIGABRT) even though the GDExtension got registered. Check `.godot/extension_list.cfg` instead of the exit code.
- **Proton costs little for compute.** The Windows build under Proton Experimental reproduced the checksum and took 0.62 ms per chunk against 0.59 ms native. Headless only; rendering under Proton is untested.
